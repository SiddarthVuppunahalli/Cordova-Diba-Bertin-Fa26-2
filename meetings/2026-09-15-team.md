## 2) Accomplished During This Meeting

Working session on the whole call: each member walked through their repositories, then the team classified the pooled incidents into one categorization of the corpus and agreed how to present it — and what to do with it — at the advisor meeting the next day.

**Categorization of the corpus — primary groups.** One category per underlying cause, each anchored to one real open-source example:

| Primary group | Simple meaning | Example from the corpus |
|---|---|---|
| Contract divergence | Developers work from different assumptions about an API, schema, signature, or behavior | React PR #28500 / issue #35424 — an internal API rename left dependent custom-renderer code on the old name |
| Change overlap \* | Developers edit the same file, method, lines, or generated section at the same time | Rails PR #43414 — concurrent migrations repeatedly changed the same ending lines of `structure.sql` |
| Dependency propagation | Different files or components depend on the same change, so one local change reaches another area | React PRs #18636 and #18649 — focus-event changes affected both Flare and the modern event system |
| Coordination and timing conflicts \*† | Developers work the same task, or in a risky order, without knowing about each other's work | Apache Kafka PR #4296 — two developers worked the same dependency task, duplicating effort |
| Integration validation failure | Changes pass separately but fail when combined, synchronized, or tested after merging | React issue #9864 — a PR passed CI but a test failed after it was merged to master |

\* more commonly found in small-scale, less organized repositories and companies; less so at large scale.
† subject to change.

**How incidents get recorded.** For each historical incident: primary **cause**, interaction **scope**, observed **outcome**. Example: a React incident is *contract divergence* (cause), *cross-component dependency* (scope), *test failure or revert* (outcome).

Decisions made:

| ID | Decision | Rationale | Alternatives rejected |
|---|---|---|---|
| D-20260915-01 | Adopt the **five primary groups** above as the classification of the mined corpus, each anchored to one real open-source example | Gives the advisor one vocabulary for the whole corpus instead of four members' separate lists, and satisfies D-20260912-03 — change overlap, dependency propagation and coordination/timing go beyond what the abstract described | Reporting each member's repository findings separately; restricting the taxonomy to the conflict types already in the abstract |
| D-20260915-02 | Record every incident as **cause + interaction scope + outcome**, not as a single label | One incident otherwise gets counted as several unrelated conflict types, which would inflate the corpus and blur what an early notification is actually worth | A single-label-per-incident taxonomy |
| D-20260915-03 | Mark **change overlap** and **coordination/timing** as characteristic of smaller, less organized repositories, and flag coordination/timing as **subject to change** | Both were rare in the large repositories we mined; the honest reading is that repository scale, not conflict physics, drives their frequency | Presenting all five groups as equally weighted across repository scale |
| D-20260915-04 | Present to the advisor as **three recurring use cases** — stale contract, false "done", unverified agent/bot claim — with the five-group table as the backing classification | Three use cases fit an eight-minute pitch and map to what our system would actually intercept; the table is the evidence behind them, not the pitch itself | Reading the five-group table aloud as the pitch |
| D-20260915-05 | **Recreate the conflict categories on a codebase we can all run**, rather than claiming the large repositories as our evaluation | Public git cannot show the laptop — uncommitted diffs, or whether a feed would have changed anyone's behaviour. The large repos are problem definition; benefit has to be measured in a lab we control | Presenting mined statistics from Kubernetes/Flutter/TensorFlow/MemPalace as the project's evaluation |
| D-20260915-06 | Use a **clone/fork of Campus Marketplace** (the CMPE 202 React + Express app) as the replay fixture, frozen at a `lab-baseline` SHA, never pushed to the Classroom original | It already contains the overlapping contracts we need — `Listing` schema vs search vs frontend `listingService`, JWT/role, the `{ success, data }` response shape, `markAsSold` — and every member can run it | Building a synthetic fixture from scratch; experimenting directly on a large open-source repo |
| D-20260915-07 | Script **four lab tasks**, each mapped to a corpus class, and compare **four conditions** — no feed / GitHub file overlap / ungated feed / gated feed | Lets us score time-to-notice, continued work on a stale contract, and acting on a false claim, with a null case that should produce no notification at all | A single end-to-end demo with no comparison condition |
