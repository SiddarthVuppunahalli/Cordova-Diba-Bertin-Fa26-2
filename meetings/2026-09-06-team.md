## 2) Accomplished During This Meeting

Worked through Prof. Jerry Gao's feedback from the 2026-09-04 presentation and finalized the resubmission abstract, due 2026-09-07 08:00.

**Instructor feedback received (2026-09-04):**
1. The abstract should implicitly tell the reader the **possible users** of the project we are building.
2. Include **statistics** that back our claim on why the product is needed, or heuristics about where it saves or provides benefit.
3. The abstract should clearly state **what changes we are tracking** — code changes, architectural changes. The instructor was confused about whether we meant videos, images, or other data genres.
4. The **project name** should clearly inform the reader what the project is and who it caters to.

Decisions made — one per feedback point:

| ID | Decision | Rationale | Alternatives rejected |
|---|---|---|---|
| D-20260906-01 | Open the abstract by naming the users directly: software teams that pair developers with AI coding agents running in parallel on one repository | Feedback #1 — the reader should not have to deduce the audience | Leaving the audience implicit in the problem framing |
| D-20260906-02 | Back the need with a cited figure: **27.67% of unmerged pull requests authored by AI coding agents contained merge conflicts**, from a 2026 study presented at the ACM International Conference on AI-Powered Software | Feedback #2 — a published measurement of the exact failure we target is stronger than a productivity heuristic. Sourced from the AgenticFlict dataset paper read under AI-20260903-02 | The 3–4 hour ERP pre-merge window heuristic from the 2026-09-02 advisor meeting, which we could not source |
| D-20260906-03 | State the tracked artifacts explicitly: **commits, local branches, uncommitted diffs, interface changes, and test results** | Feedback #3 — the instructor read the unscoped word "changes" as possibly covering video, image, or other data genres | Keeping the general phrasing "code and architectural changes" |
| D-20260906-04 | Rename the project to **"Verified Code-Change Awareness for AI-Assisted Software Teams"** | Feedback #4 — the name now states the artifact (code changes), the property (verified awareness), and the audience (AI-assisted software teams) | Keeping the original name |
| D-20260906-05 | Frame the mechanism as an **evidence gate** rather than a merge queue: validators confirm the referenced code or test supports a claim before it is shared, admitted claims retain author, commit and evidence, and reach only teammates whose current work they affect | Agents report intended edits as completed and repeat facts that held at an earlier commit — unverified information is worse than none, because teammates build on it.
